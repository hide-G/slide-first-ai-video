# MediaConvert pipeline: FFmpeg elimination and service-based video assembly

This change replaces the FFmpeg-based clip+concat pipeline with AWS MediaConvert for final video rendering, eliminates all Docker/container dependencies, and adds a Marp Core + Chromium-based slide generation stage. The architecture moves from a 5-stage Lambda pipeline (pages/audio/captions/clips/concat) to a 4-stage one (pages/audio/captions/video) where the video stage submits a single MediaConvert job that concatenates all page inputs. Key supporting changes include WAV-based audio (enabling exact PCM duration calculation without ffprobe), frame-aligned timing to prevent drift, and esbuild bundling to fix the existing `Runtime.ImportModuleError` Lambda startup failures.

Watch for: Lambda timeout vs MediaConvert polling duration mismatch (confirmed), missing `MEDIACONVERT_ENDPOINT` env var in CDK (confirmed), silent fail-open when polling exhausts without terminal status (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The mediaconvert-worker Lambda polls for job completion with a 10-second interval and 180 max attempts (30 minutes total), but the CDK construct sets the Lambda timeout to 300 seconds (5 minutes). Any MediaConvert job taking longer than 5 minutes will cause a Lambda timeout. The design doc specified using Step Functions `IntegrationPattern.RUN_JOB` to avoid exactly this problem; the implementation uses a self-polling Lambda instead.

The CDK construct does not set `MEDIACONVERT_ENDPOINT` as an environment variable, but the Lambda code reads it from `process.env.MEDIACONVERT_ENDPOINT` and passes it to the `MediaConvertClient` constructor. Without this, the SDK will use the default global endpoint rather than the account-specific endpoint, which may fail for CreateJob/GetJob calls in ap-northeast-1.

If the polling loop exhausts without reaching a terminal job status (COMPLETE/ERROR/CANCELED), execution falls through to write `stages.video = "done"` to the manifest — a fail-open path that marks the video stage as complete while the job may still be in progress.

The marp-render build script hardcodes pnpm virtual store paths for `@sparticuz/chromium@133.0.0` and `puppeteer-core@24.2.0`. If these versions ever change, the build falls through to a less-tested root `node_modules` lookup path. Acceptable given the design doc mandates these exact versions.

## MediaConvert worker: timeout and polling

The Lambda timeout is 300 seconds but the polling loop can run for up to 30 minutes (180 attempts * 10s). In practice the Lambda will be killed at 5 minutes regardless of polling state. For a 2-page deck (53s output), MediaConvert typically completes in 60-120 seconds so this works. For longer presentations the Lambda will timeout.

If the polling loop exhausts `MAX_POLL_ATTEMPTS` without hitting a terminal state, execution falls through:

```typescript
// After the for-loop completes without break:
manifest.stages.video = "done";  // writes "done" even though job may still be PROGRESSING
await writeManifest(bucket, manifestKey, manifest);
return { success: true, outputDurationMs };  // outputDurationMs is still 0
```

This is a fail-open bug. The handler should throw an error if the loop exits without reaching COMPLETE.

## Missing MEDIACONVERT_ENDPOINT environment variable

The CDK construct sets `BUCKET_NAME` and `MEDIACONVERT_ROLE_ARN` but not `MEDIACONVERT_ENDPOINT`:

```typescript
environment: {
  BUCKET_NAME: props.projectBucket.bucketName,
  MEDIACONVERT_ROLE_ARN: this.mediaConvertRole.roleArn,
},
```

AWS MediaConvert requires the account-specific endpoint (obtained via `DescribeEndpoints`) rather than the regional service endpoint. Without it, CreateJob calls will fail with an endpoint resolution error. Options:
- Add `MEDIACONVERT_ENDPOINT` as a construct parameter (resolved at deploy time via custom resource or manual config)
- Add a `DescribeEndpoints` call in the Lambda at startup (requires `mediaconvert:DescribeEndpoints` IAM permission)

## marp-render: pnpm version-pinned paths

The build script hardcodes:

```javascript
const chromiumPnpmDir = join(NODE_MODULES, ".pnpm/@sparticuz+chromium@133.0.0/node_modules");
const puppeteerPnpmDir = join(NODE_MODULES, ".pnpm/puppeteer-core@24.2.0/node_modules");
```

The fallback (`else` branch) looks in root `node_modules` and relies on `dereference: true` in `cp()`. This path is untested. A version bump to either package will silently switch to the fallback without warning in CI.

## Polly-worker PCM duration path

The duration calculation uses the raw PCM buffer length *before* the WAV header is prepended, avoiding double-counting the 44 header bytes:

```typescript
const audioDurationSec = calculatePcmDurationSec(pcmBuffer.length, sampleRate, 16, 1);
const wavHeader = createWavHeader(pcmBuffer.length, sampleRate, 16, 1);
const wavBuffer = Buffer.concat([wavHeader, pcmBuffer]);
```

This ordering is correct but relies on `pcmBuffer` being the direct Polly `AudioStream` response. If an intermediate transform were added that mutated the buffer length, the duration would silently drift.
