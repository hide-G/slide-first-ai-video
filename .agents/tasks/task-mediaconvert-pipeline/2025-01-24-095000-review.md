# MediaConvert pipeline v2: fixes for timeout, endpoint, and polling exhaustion

Three of the four v1 issues are resolved. The Lambda timeout is now 900s with MAX_POLL_ATTEMPTS reduced to 85 (850s total polling, within timeout). The endpoint resolution uses a cached `DescribeEndpoints` call at runtime with the corresponding IAM permission added. Polling exhaustion now throws instead of falling through. The fourth issue — using a polling Lambda instead of the CDK `MediaConvertCreateJob` with `IntegrationPattern.RUN_JOB` as the design doc mandates — remains unaddressed but is no longer functionally broken.

Watch for: Design doc deviation on polling Lambda vs Step Functions RUN_JOB integration (confirmed), Step Functions pipeline proceeds on stage failure without checking Lambda return value (confirmed, pre-existing pattern).

**Verdict**: APPROVED

## High-level view

The timeout/polling math is sound: 85 attempts * 10s = 850s maximum, with 50s headroom before the 900s Lambda timeout. The endpoint resolution falls back to `DescribeEndpoints` (cached per container) when the env var isn't set, with the IAM permission granted. Polling exhaustion throws with the job ID, caught by the outer try/catch which writes `stages.video = "failed"` — fail-closed.

The design doc explicitly says "完了待ちには CDK の `MediaConvertCreateJob` タスクを `IntegrationPattern.RUN_JOB` で使ってください。ポーリング用のLambdaを自作しないでください。" CDK ships `MediaConvertCreateJob` with RUN_JOB support (verified in `aws-cdk-lib@2.189.0`). The current polling approach works for the expected workload (2-10 page decks, 30s-5min videos) but imposes a 900s hard ceiling with no upgrade path short of refactoring.

The state machine chains stages without checking `$.Payload.success` between them. If audio fails and returns `{ success: false }`, captions and video still execute on a broken manifest. Pre-existing pattern from main, not introduced here.

## Polling Lambda ceiling vs RUN_JOB

CDK's `MediaConvertCreateJob` supports `IntegrationPattern.RUN_JOB`, which uses EventBridge to detect job completion — no Lambda polling, no timeout ceiling.

The refactoring path:
1. Keep `job-builder.ts` as-is (already produces correct job JSON)
2. Add a thin "prepare-video" Lambda that reads the manifest, calls `buildMediaConvertJob`, and returns the job JSON
3. Replace the `VideoStage` `LambdaInvoke` with a `MediaConvertCreateJob` task consuming the prepare-video output
4. Add a post-job Lambda to read `OutputGroupDetails[0].OutputDetails[0].DurationInMs` and update the manifest

Mechanical change, touches CDK construct and state machine definition. Current polling works for the expected workload (well under 850s encode time).

## Pipeline cascade on failure (pre-existing)

The MediaConvert worker is the first stage that explicitly writes `"failed"` to the manifest and returns `success: false` (the old clip/concat workers threw errors that caused Step Functions task failures). Since video is the terminal stage, this difference in error signaling has no downstream impact. For the earlier stages (pages, audio, captions), the cascade-on-failure behavior is unchanged from main.
