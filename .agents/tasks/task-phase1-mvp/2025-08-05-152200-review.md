# Slide-first AI video: Phase 1 MVP implementation

A pnpm monorepo with 15 workspace packages implements the Phase 1 MVP of a slide-first AI video generator. The implementation covers Marp rendering, Polly TTS, caption generation, FFmpeg/Hyperframes renderers behind a port interface, 7 REST API endpoints, CDK infrastructure with Step Functions, and a golden-set evaluation framework. The architecture follows the design document closely in structure and naming, with the renderer port, timing resolver, and caption pipeline faithfully implementing the specified contracts. However, the infrastructure layer contains critical wiring errors that would prevent deployment from working end-to-end.

Watch for: DynamoDB table model mismatch between CDK and Lambda code (confirmed), environment variable naming conflicts that would silently break at runtime (confirmed), and the Hyperframes renderer being a stub with only `plan()` implemented (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The DynamoDB data layer has a fundamental design split: the CDK creates 4 separate tables with different key schemas, but all Lambda code uses a single-table pattern writing to one `TABLE_NAME` with composite PK/SK keys like `PROJECT#id`. Deploying this stack would result in items going to a table whose key schema doesn't match the PK/SK being sent. The videos handler reads `VIDEO_STATE_MACHINE_ARN` but CDK exports `RENDER_STATE_MACHINE_ARN`; the deliverables and versions handlers read `BUCKET_NAME` but CDK sets `PROJECT_BUCKET`. These are silent failures at runtime.

The core domain logic is well-tested and correctly implements the design document's timing, caption, and manifest specifications. The renderer port has a fully functional FFmpeg implementation, but the CDK render state machine references a Lambda code path (`marp-render/dist`) that doesn't contain action-based dispatch for the `plan/renderChunk/assemble` protocol.

The content state machine's approval step is a `sfn.Pass`, meaning the pipeline executes straight through without pausing for user approval — violating the design's explicit requirement that `SLIDE_APPROVED` gates video generation.

S3 IAM grants use literal prefixes (`audio/*`, `slides/*`) that don't match the actual key structure (`userId/projectId/versions/vNNNN/audio/...`), causing AccessDenied at runtime.

## DynamoDB table model disconnect

The CDK StorageConstruct creates four tables:

```
testapp-dev-projects  (PK: userId, SK: projectId)
testapp-dev-versions  (PK: projectId, SK: version)
testapp-dev-jobs      (PK: jobId)
testapp-dev-idempotency (PK: idempotencyKey)
```

The Lambda code (`lambdas/api/src/db/`) uses a single-table design on one `TABLE_NAME`:

```typescript
// projects.ts
PK: `PROJECT#${project.projectId}`, SK: `META`
GSI1PK: `USER#${project.userId}`, GSI1SK: `PROJECT#${project.createdAt}`

// versions.ts
PK: `PROJECT#${version.projectId}`, SK: `VERSION#0001`

// jobs.ts
PK: `JOB#${job.jobId}`, SK: `META`
GSI1PK: `PROJECT#${job.projectId}`, GSI1SK: `JOB#${job.createdAt}`

// idempotency.ts
PK: `IDEMPOTENCY#${key}`, SK: `META`
```

The projects table expects `userId` as the partition key, but the Lambda sends `PK: "PROJECT#proj-123"` — DynamoDB would reject because the attribute names don't match the key schema. The Lambda's single-table design is the architecturally correct choice for this workload. The fix is to consolidate CDK to one table with `PK` (string) and `SK` (string) as keys, plus a GSI on `GSI1PK`/`GSI1SK`.

## Environment variable wiring

Three sets of naming conflicts:

| Lambda reads | CDK provides |
|---|---|
| `TABLE_NAME` | `PROJECTS_TABLE`, `VERSIONS_TABLE`, `JOBS_TABLE`, `IDEMPOTENCY_TABLE` |
| `BUCKET_NAME` | `PROJECT_BUCKET` |
| `VIDEO_STATE_MACHINE_ARN` | `RENDER_STATE_MACHINE_ARN` |

These silently fall back to empty strings (the `?? ""` defaults), causing runtime errors when S3/DynamoDB calls fail or state machines never starting.

## Render pipeline Lambda dispatch gap

The CDK `RenderStateMachineConstruct` points its render Lambda at `../lambdas/marp-render/dist`. The render state machine sends events with `action: "plan"`, `action: "renderChunk"`, and `action: "assemble"`. But the marp-render Lambda's handler processes `MarpRenderEvent` (which expects `outputs: ["pdf", "pptx", "png"]`). There's no action-based dispatch logic. The render Lambda needs its own handler that instantiates `FfmpegRenderer` and routes by action field.

## IAM grants and S3 key path mismatch

The Polly Worker's S3 write grant uses prefix `audio/*`:

```typescript
props.projectBucket.grantWrite(this.handler, "audio/*");
```

But actual S3 keys are:

```
user-456/proj-123/versions/v0001/audio/slide-001.pcm
```

The grant pattern doesn't match, so writes fail with AccessDenied. Similarly, the Marp Lambda grants write to `slides/*` and `versions/*`, but actual keys are `user-456/proj-123/versions/v0001/slides/deck.001.png`.

## Content state machine approval gap

The content state machine has a `WaitForApproval` step implemented as `sfn.Pass`, which means execution continues immediately. The design requires the user to approve via API before video generation begins. This needs either a Task state with `.waitForTaskToken()` callback pattern or splitting the state machine at the approval boundary.

## Renderer plan() duplication

The `plan()` method in `HyperframesRenderer` and `FfmpegRenderer` contains identical logic for computing `totalFrames`, `chunkCount`, `intermediatePrefix`, and reading `outputConfig` from the manifest. This should be extracted into a shared utility in `@slide-first/core` or `@slide-first/renderer-port` to prevent divergence as these implementations evolve independently.

## Test coverage gaps

Not tested: integration between CDK-provisioned infrastructure and Lambda code (the env var mismatches would only surface here), end-to-end flow through the state machine, actual Marp CLI execution, actual FFmpeg execution (tests mock `execFile`), and the Hyperframes render path beyond `plan()`.
