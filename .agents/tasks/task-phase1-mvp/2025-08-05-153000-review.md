# Slide-first AI video: Phase 1 MVP (v2 review)

The 7 CDK-to-Lambda integration issues identified in v1 have all been correctly fixed: DynamoDB uses single-table design with PK/SK composite keys and GSI1, env vars are consistently named (`TABLE_NAME`, `BUCKET_NAME`, `VIDEO_STATE_MACHINE_ARN`), a new `render-worker` Lambda dispatches plan/renderChunk/assemble actions to the FFmpeg renderer, S3 grants use full bucket access via `"*"`, and the content state machine's approval step uses an SQS `waitForTaskToken` callback pattern.

Watch for: The approve API handler updates DynamoDB status but never calls `SendTaskSuccess` to resume the paused state machine (confirmed). The render state machine's Map state references `$.planResult.Payload.chunks` but the plan output has no `chunks` array — runtime failure (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The approval gate is architecturally half-complete. The content state machine correctly pauses via `SqsSendMessage` with `WAIT_FOR_TASK_TOKEN`, sending the task token and project metadata to an SQS queue. But the approve API endpoint only updates the version's DynamoDB status to `SLIDE_APPROVED` — it never reads the task token from SQS or calls `SendTaskSuccess` to resume the state machine. The approval queue is exposed as `contentStateMachine.approvalQueue` in the CDK construct but never passed to the API construct; the API Lambda has no queue URL and no IAM permissions for SQS or `states:SendTaskSuccess`.

The render state machine's Map state has `itemsPath: "$.planResult.Payload.chunks"`, but `FfmpegRenderer.plan()` returns a `RenderPlan` with `chunkCount: number` — no `chunks` array exists. Step Functions will raise a `States.Runtime` error because the path doesn't resolve to an array. The plan needs to emit a `chunks` array for the Map state to iterate over.

The slide-generator Lambda exists as a fully-tested package but is not wired into the content state machine (the GenerateContent step is a Pass placeholder). The timing resolver and caption generator are also Pass states. These are acceptable scaffolding provided the blocking issues above are fixed first.

## Approval token gap

The content state machine sends a message to the approval SQS queue:

```typescript
const waitForApproval = new tasks.SqsSendMessage(this, "WaitForApproval", {
  queue: this.approvalQueue,
  messageBody: sfn.TaskInput.fromObject({
    "taskToken": sfn.JsonPath.taskToken,
    "projectId.$": "$.projectId",
    "userId.$": "$.userId",
    "versionNumber.$": "$.versionNumber",
  }),
  integrationPattern: sfn.IntegrationPattern.WAIT_FOR_TASK_TOKEN,
});
```

To resume execution, the approve handler must:

1. Receive the message from the queue (filtered by projectId/versionNumber)
2. Extract the task token
3. Call `SFNClient.send(new SendTaskSuccessCommand({ taskToken, output: '{}' }))`
4. Delete the message from the queue

Currently `handleApprove` calls `updateVersionStatus(projectId, versionNumber, "SLIDE_APPROVED")` and returns 200. The approval queue is exposed as `contentStateMachine.approvalQueue` in the CDK construct but never passed to the API construct. The API Lambda lacks the queue URL env var and has no IAM permissions for `sqs:ReceiveMessage`, `sqs:DeleteMessage`, or `states:SendTaskSuccess`.

An alternative design worth considering: store the task token in DynamoDB alongside the version record when the state machine starts (via a Lambda step before WaitForApproval). This avoids the queue-scan problem of matching an SQS message to a specific projectId/versionNumber pair.

## Render Map state `chunks` path mismatch

The render state machine's Map state:

```typescript
const mapChunks = new sfn.Map(this, "MapRenderChunks", {
  itemsPath: "$.planResult.Payload.chunks",
  maxConcurrency: 10,
});
```

The `FfmpegRenderer.plan()` return value (lines 60–87 of `ffmpeg-renderer.ts`):

```typescript
return {
  totalFrames,
  chunkCount,    // number, not array
  fps,
  width,
  height,
  videoBitrateKbps,
  intermediatePrefix,
  input,
};
```

`RenderPlan` in `shared-types` defines `chunkCount: number` with no `chunks` property. The Map state requires an array at the specified path. The natural fix is to have `plan()` return a `chunks` array:

```typescript
chunks: Array.from({ length: chunkCount }, (_, i) => ({
  plan: { totalFrames, chunkCount, fps, width, height, videoBitrateKbps, intermediatePrefix, input },
  chunkIndex: i,
}))
```

This aligns with the render worker's `RenderChunkEvent` type which expects `{ plan, chunkIndex }` at `event.chunk`. Add `chunks` to the `RenderPlan` type definition.

## Content state machine placeholder steps

Four steps in the content state machine are Pass placeholders: `GenerateContent`, `SaveDeckToS3`, `TimingResolver`, and `CaptionGenerator`. The slide-generator Lambda package is fully implemented (Bedrock Converse, prompt construction, parser, validator) but has no CDK construct and no state machine integration. The content pipeline cannot produce actual slide content through the state machine — the parallel Marp+Polly step will receive passthrough input without a `deck.md` S3 key or slide metadata.
