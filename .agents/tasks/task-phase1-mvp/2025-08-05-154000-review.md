## High-level view

The three v2 fixes are solid. The approval handler is architecturally complete: SQS receive, token matching, `SendTaskSuccess`, message deletion, DynamoDB update — with proper IAM grants and env var wiring in CDK. The render Map-over-chunks flow is type-safe end-to-end now that `RenderPlan` includes a `chunks` array and the Map state iterates it. The slide-generator Lambda is integrated as a real `LambdaInvoke` step.

The remaining issue is a Step Functions data path problem in the content state machine. After `GenerateContent` stores its output at `$.bedrockResult`, the Polly Map state references `$.slides` (top-level) which doesn't exist — the actual path is `$.bedrockResult.Payload.slides`. The same pattern affects the Marp step: it doesn't specify a `payload` parameter, so Step Functions passes the entire state (including `projectId`, `userId`, etc.) rather than the `MarpRenderEvent` shape the Lambda expects. Both will fail at runtime when the parallel processing step executes.

## Content state machine data path gap

The content state machine chains: `GenerateContent` (LambdaInvoke, `resultPath: "$.bedrockResult"`) → `SaveDeckToS3` (Pass) → `WaitForApproval` → `ParallelMarpPolly`.

After GenerateContent, the state looks like:

```
{
  "projectId": "...",
  "userId": "...",
  "versionNumber": 1,
  "theme": "...",
  "bedrockResult": {
    "Payload": {
      "deckKey": "...",
      "slideCount": 10,
      "slides": [ { "slideNumber": 1, "presenterNote": "...", ... }, ... ]
    }
  }
}
```

The Polly Map state at line 122 of `content-state-machine-construct.ts`:

```typescript
const pollyMapState = new sfn.Map(this, "PollyMapOverSlides", {
  itemsPath: "$.slides",          // <-- should be $.bedrockResult.Payload.slides
  resultPath: "$.pollyResults",
  maxConcurrency: 5,
});
```

Step Functions requires `itemsPath` to resolve to an array. `$.slides` is undefined, triggering a `States.Runtime` error. The fix is either to change `itemsPath` to `"$.bedrockResult.Payload.slides"`, or to add a Pass step before the Parallel that flattens the data.

Similarly, the Marp LambdaInvoke step doesn't specify a `payload`:

```typescript
const invokeMarp = new tasks.LambdaInvoke(this, "InvokeMarpLambda", {
  lambdaFunction: props.marpLambda,
  resultPath: "$.marpResult",
  retryOnServiceExceptions: true,
});
```

Without an explicit `payload`, Step Functions sends the entire effective state as the Lambda event. The Marp handler expects `MarpRenderEvent` with fields `deckMarkdown`, `s3Bucket`, `s3Prefix`, `outputs` — none of which exist in the state at that point. It would need something like:

```typescript
payload: sfn.TaskInput.fromObject({
  "projectId.$": "$.projectId",
  "userId.$": "$.userId",
  "version.$": "$.versionNumber",
  "deckMarkdown.$": "$.bedrockResult.Payload.rawMarkdown",  // or read from S3
  "s3Bucket.$": "$.s3Bucket",
  "s3Prefix.$": "$.s3Prefix",
  outputs: ["pdf", "png"],
}),
```

The same applies to the Polly worker: each iteration item from the Map needs to be shaped into a `PollyWorkerEvent` (with `presenterNote`, `voiceId`, `engine`, `sampleRate`, `s3Bucket`, `s3Prefix`, etc.). The Map iterator just passes through whatever the item is — currently a `SlideOutput` object — without mapping it to the Polly event shape.

These are runtime failures that will prevent the pipeline from progressing past the approval gate, but they're localized to the state machine definition wiring and don't affect any of the Lambda implementations themselves, which are well-structured.
