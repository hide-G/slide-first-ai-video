# Complete architecture rebuild: manifest-driven 5-stage video pipeline

The application was rewritten from a version/job-based content pipeline with teasers, approval queues, and PCM audio into a manifest-driven 5-stage video production system. Five independent Lambda stages (pages, audio, captions, clips, concat) are orchestrated by a single Step Functions state machine. The frontend moves from a multi-page project/version/job CRUD interface to a two-studio wizard pattern (slide studio, video studio) matching provided HTML mockups.

Watch for: The state machine definition does not implement the `startFromStage` partial-retry feature advertised by the API -- the linear chain always executes all 5 stages (confirmed). The event shape the state machine sends to caption/clip/concat workers does not match what those handlers expect -- this will fail at runtime (confirmed). Presigned upload URLs use `PutObjectCommand` without size or content-type enforcement at the S3 level (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The data contract uses a zod-validated `manifest.json` per project with a separate `validateInvariants` function checking cross-field rules. The S3 layout is `users/{userId}/projects/{projectId}/` with well-defined subdirectories, replacing the old version-numbered prefix.

The 5-stage pipeline runs as a linear Step Functions chain with Map states for audio and clips parallelism. The pipeline does not implement per-stage skipping or partial restart despite the API accepting a `startFromStage` parameter -- the state machine chains all stages unconditionally. Additionally, the payload shape the state machine sends (`s3Bucket`, `s3Prefix`) does not match the Lambda handler event interfaces (`bucket`, `manifestKey`), which will cause runtime failures.

The API Lambda exposes 13 methods covering outline generation, deck generation, source upload, output settings, narration management, and render lifecycle. Ownership verification on every request uses a GSI query; a direct `GetItem` on the primary key (which already includes the user) would be cheaper and inherently prove ownership without needing the GSI.

The frontend implements a home hub and two multi-step wizards matching the HTML mockups. The video studio handles SSML editing with a movable cheatsheet panel, output configuration, and a 5-stage progress display.

The renderer-ffmpeg package exports three command-builder modules (clip, concat, probe). The concat builder's `subtitles=` filter does not escape `srtPath` -- a latent injection risk if the path ever contains FFmpeg filter metacharacters.

<details>
<summary>Issues (5)</summary>

1. **startFromStage is a no-op** -- The API accepts `startFromStage` and passes it in the Step Functions execution input, but the state machine definition (`render-state-machine-construct.ts`) chains all 5 stages unconditionally with no Choice state to skip completed stages. Implement skip logic using a Choice state per stage, or remove the parameter from the API to avoid misleading callers.
2. **Event shape mismatch causes runtime failure** -- The state machine sends `{ stage, s3Bucket, s3Prefix, ... }` to caption-worker, clip-worker, and concat-worker, but those handlers expect `{ bucket, manifestKey }`. Neither field name matches. Either align the Lambda event interfaces to the state machine payload, or add Pass states in the state machine to reshape the payload.
3. **Presigned upload URL has no size limit** -- `handleSourceUploadUrl` generates a presigned PutObject URL with no `Content-Length` condition. A malicious or buggy client can upload arbitrarily large files. Add a content-length condition via presigned POST, or validate object size in `handleRegisterSource` before allowing downstream stages to proceed.
4. **Ownership check uses GSI when primary key suffices** -- `verifyProjectOwnership` queries GSI1 on every mutating request. Since the table's primary key is `PK=USER#{userId}, SK=PROJECT#{projectId}`, a direct `GetItem` would be faster, cheaper, and inherently prove ownership without needing the GSI.
5. **Concat subtitles filter path not escaped** -- `buildConcatArgs` interpolates `srtPath` into `-vf "subtitles=${srtPath}"` without escaping FFmpeg filter metacharacters (`:`, `[`, `'`). Currently low risk since the path is always `/tmp/concat-work/captions.srt`, but a defensive escape would prevent future breakage.

## State machine vs API contract mismatch on partial retry

The `StartRenderSchema` accepts `startFromStage` (one of the 5 stage names), and `handleStartRender` passes it through to the Step Functions execution input:

```typescript
const executionInput = {
  ...
  startFromStage: body.startFromStage ?? "pages",
};
```

However, `RenderStateMachineConstruct` defines a linear chain:

```typescript
const definition = pagesStage
  .next(audioMap)
  .next(captionsStage)
  .next(clipsMap)
  .next(concatStage);
```

There is no Choice state reading `$.startFromStage` to skip earlier stages. An API caller passing `startFromStage: "clips"` will still run pages, audio, and captions first. The spec (section 6) describes independent stage re-run as a requirement. Implementing this requires a Choice state at the beginning that branches into the correct starting point, or parallel definition branches.

## Event shape mismatch between state machine and Lambda handlers

The state machine's `CaptionsStage` task sends:

```json
{ "stage": "captions", "projectId": "...", "userId": "...", "renderId": "...", "s3Bucket": "...", "s3Prefix": "...", "audioResults": "..." }
```

But `caption-worker/src/index.ts` defines:

```typescript
export interface CaptionsEvent {
  bucket: string;
  manifestKey: string;
}
```

The handler destructures `event.bucket` and `event.manifestKey` -- neither of which is provided by the state machine payload (it sends `s3Bucket` not `bucket`, and `s3Prefix` not `manifestKey`). The same pattern holds for `clip-worker` and `concat-worker`.

This will cause runtime failures on the first execution. The fix is either to align the Lambda event interfaces to match what the state machine sends, or to add a Pass state in the state machine that reshapes the payload before each Lambda invocation.

## Presigned upload without size enforcement

In `source.ts`:

```typescript
const command = new PutObjectCommand({
  Bucket: BUCKET_NAME,
  Key: fileKey,
  ContentType: body.contentType,
});
const uploadUrl = await getSignedUrl(s3Client, command, { expiresIn: 3600 });
```

The presigned URL allows uploading any file of any size. S3 presigned POSTs support `content-length-range` conditions; presigned PUTs can include `Content-Length` in the signed headers. At minimum, validate the uploaded object's actual content type and size in `handleRegisterSource` before allowing downstream stages to proceed.

## DynamoDB ownership verification via GSI is unnecessarily expensive

The project record uses `PK=USER#{userId}, SK=PROJECT#{projectId}` with a GSI (`GSI1PK=PROJECT#{projectId}, GSI1SK=META`). The `getProject` function queries GSI1 to find a project by ID regardless of user. Then `verifyProjectOwnership` compares the returned `userId` field.

Since the JWT already contains the `sub` claim and the project table's primary key includes the user, a direct `GetItem` on `PK=USER#{userId}, SK=PROJECT#{projectId}` would be both faster (single-item read vs query) and inherently proves ownership -- if the item exists under that user's partition, they own it.

## Concat subtitles filter path injection

`buildConcatArgs` interpolates `srtPath` directly:

```typescript
args.push("-vf", `subtitles=${srtPath}`);
```

FFmpeg's subtitles filter uses `:` as an option separator and `'` for quoting. A path like `/tmp/project:abc/captions.srt` would break the filter expression. In practice the concat worker constructs paths like `/tmp/concat-work/captions.srt` so this is unlikely to trigger, but it represents a latent fragility. Wrapping the path in FFmpeg's escaping syntax (`subtitles='path'` with internal `'` escaped as `'\''`) would make this robust.

## Test coverage gaps

291 tests pass. Not tested: the runtime event shape contract between the state machine and the Lambda handlers (the mismatch described above would not be caught since each Lambda is tested in isolation with its own event shape). Integration between `handleStartRender` and the actual state machine execution is also untested -- the CDK test validates the state machine definition structure but not the payload flow.
