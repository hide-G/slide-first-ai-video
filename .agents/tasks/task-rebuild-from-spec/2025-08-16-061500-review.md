# Manifest-driven 5-stage pipeline rebuild — v2 review

All five issues from the v1 review have been addressed: the state machine now has a Choice state for `startFromStage`, the caption/clip/concat worker event interfaces are aligned to `{ s3Bucket, s3Prefix }`, HeadObject validation blocks oversized uploads, ownership uses direct GetItem, and FFmpeg filter paths are escaped. However, two of the five workers (marp-render and polly-worker) still have event interface mismatches, and the Map-state-per-page architecture conflicts with how those workers are coded (they process all pages in a single invocation).

Watch for: marp-render and polly-worker still expect `{ bucket, manifestKey }` but the state machine sends `{ s3Bucket, s3Prefix }` — the event shape fix applied to stages 3-5 was not applied to stages 1-2 (confirmed). The audio and clips Map states iterate on `$.pagesResult.Payload.pages` but marp-render returns `{ success, pageCount }` with no `pages` array — the Map state will fail (confirmed). Plain-text narration is wrapped in `<speak>` without XML-escaping non-lexicon text, which will cause Polly to reject scripts containing `&` or `<` (confirmed). The presigned upload URL sets `ContentLength` to exactly 100MB rather than a maximum, which will reject any upload not exactly that size (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The state machine's Choice state for `startFromStage` is now in place, routing executions to the correct starting stage based on the input parameter. The state machine's payload contract with stages 3-5 (captions, clips, concat) uses `{ s3Bucket, s3Prefix }` and those handlers are aligned. Stages 1-2 (marp-render, polly-worker) have not been updated — they still destructure `event.bucket` and `event.manifestKey` from an event shape the state machine no longer sends.

The audio and clips stages use Map states that iterate per-page, but both polly-worker and clip-worker read the manifest and process ALL pages in a single handler invocation. When invoked N times in parallel by the Map state, each invocation does the full workload (N×N total operations) and races on manifest writes. The clip-worker already accepted `{ s3Bucket, s3Prefix }` as its event interface, but its logic processes all pages regardless of which "page" the Map state intended it to process.

The `buildSpeakTag` function in polly-worker passes plain-mode text into `<speak>` tags without XML-escaping characters that are syntactically meaningful in SSML. The `applyLexicon` function escapes text only inside the substitution tag attributes, leaving the surrounding plain text with its original `&`, `<`, `>` characters intact.

1. **Stages 1-2 event shape still mismatched** — `marp-render` expects `{ bucket, manifestKey }` and `polly-worker` expects `{ bucket, manifestKey }`, but the state machine sends `{ s3Bucket, s3Prefix, stage, projectId, ... }`. Either add a `pages` array to the marp-render return value, or switch the Map states to a different data source (e.g., generate the page list from `pageCount`).
3. **All-pages-in-one-invocation vs per-page Map state** — polly-worker and clip-worker are coded to process all pages from the manifest in a loop, but the state machine invokes them once per page via a Map state. This causes N² work and manifest write races. Redesign the workers to process a single page per invocation (using the `page` field from the Map state input), or change the state machine to invoke each worker once for all pages (remove the Map state, single invocation).
4. **Plain text not XML-escaped before Polly** — `buildSpeakTag` wraps plain-mode text in `<speak>` without escaping `&`, `<`, `>`. If any narration script contains these characters (common in Japanese text like "A&B" or "x<y"), Polly will return a validation error. Escape non-lexicon text before wrapping.
5. **Presigned URL ContentLength is exact, not maximum** — `PutObjectCommand` with `ContentLength: 100MB` and signing `content-length` means the upload must be exactly 100MB. The HeadObject check in `handleRegisterSource` provides a safety net, but the presigned URL itself will reject normal uploads. Remove `ContentLength` from the PutObjectCommand (the HeadObject check is sufficient), or switch to presigned POST with a `content-length-range` condition.

## Stages 1-2 event shape vs state machine payload

The v1 review identified this mismatch for stages 3-5, which have been fixed. Stages 1-2 remain broken. The state machine's PagesStage sends:

```json
{ "stage": "pages", "projectId": "...", "userId": "...", "renderId": "...", "s3Bucket": "...", "s3Prefix": "..." }
```

But `marp-render/src/index.ts` line 46 destructures:

```typescript
const { bucket, manifestKey } = event;
```

Neither `bucket` nor `manifestKey` exists in the payload. The handler will read `undefined` for both, then fail attempting `GetObjectCommand({ Bucket: undefined, Key: undefined })`.

The same pattern exists in `polly-worker/src/index.ts` line 51. The AudioPerPage task sends `{ stage, page, s3Bucket, s3Prefix, ... }` and the handler destructures `{ bucket, manifestKey }`.

## Map state references non-existent pages array

Both Map states in the state machine use:

```typescript
itemsPath: "$.pagesResult.Payload.pages"
```

The marp-render Lambda returns:

```typescript
return { success: true, pageCount: pngFiles.length };
```

There is no `pages` field. Step Functions will fail with an error like "Invalid path '$.pagesResult.Payload.pages': No results for path". The marp-render Lambda needs to return a `pages` array (e.g., `[{ pageNumber: 1 }, { pageNumber: 2 }, ...]`) for the Map states to iterate over.

## Per-page Map invocation vs all-pages processing

The clip-worker's handler:

```typescript
export const handler = async (event: ClipsEvent): Promise<ClipsResult> => {
  // ...
  for (const page of manifest.pages) { // processes ALL pages
    // ... downloads, ffmpeg, uploads for every page
  }
};
```

The state machine invokes this once per page item from the Map state. With 5 pages, clip-worker is invoked 5 times, each processing all 5 pages = 25 total clip generations instead of 5. Each invocation also writes the manifest with `stages.clips = "running"` / `"done"`, creating a race condition where concurrent writes from different invocations can overwrite each other.

The polly-worker has the same pattern: processes all pages from the manifest, but is invoked per-page by the Map state.

The fix is either: (a) make each worker process only the single page identified by the Map state's `page` input, or (b) remove the Map states and invoke each worker once to handle all pages.

## Plain text XML escaping in polly-worker

In `polly-worker/src/index.ts`:

```typescript
function buildSpeakTag(text: string, mode: "plain" | "ssml"): string {
  if (mode === "ssml") {
    return `<speak>${text}</speak>`;
  }
  return `<speak>${text}</speak>`; // no escaping for plain mode
}
```

`applyLexicon` only escapes text within the `alias=""` or `ph=""` attributes of the SSML tags it inserts. The remaining text (everything that doesn't match a lexicon entry) is passed raw. A script like "Slide 1 & 2の解説" will produce `<speak>Slide 1 & 2の解説</speak>`, which is invalid XML and will cause Polly to return an error.

The fix: in plain mode, XML-escape the entire text before passing it to `applyLexicon`, then let `applyLexicon` insert its SSML tags into the already-escaped content. Alternatively, escape the non-matched portions after lexicon application.

## Presigned upload ContentLength semantics

In `source.ts`:

```typescript
const command = new PutObjectCommand({
  Bucket: BUCKET_NAME,
  Key: fileKey,
  ContentType: body.contentType,
  ContentLength: MAX_UPLOAD_SIZE_BYTES, // 100MB
});

const uploadUrl = await getSignedUrl(s3Client, command, {
  expiresIn: 3600,
  signableHeaders: new Set(["content-length"]),
});
```

Setting `ContentLength` on the PutObjectCommand with signed headers means the presigned URL's signature includes `content-length: 104857600`. A client uploading a 5MB file with `Content-Length: 5242880` will get a signature mismatch error. Only a 100MB upload would match.

The `handleRegisterSource` HeadObject check that validates actual size after upload is the real protection. The presigned URL `ContentLength` should be removed, or the approach should switch to presigned POST which supports `content-length-range` conditions as `["content-length-range", 1, MAX_UPLOAD_SIZE_BYTES]`.
