# The Problem: Scaling Real-Time Analytics

Our event processing pipeline hit 50K events/sec limit, causing data loss during peak hours.

<!-- presenterNote: The legacy system used a single Kafka partition with synchronous processing. During Black Friday, we lost approximately 15% of events when throughput exceeded 50K/sec. -->
<!-- keyPoints: ["Pipeline limited to 50K events/sec", "15% data loss during peak traffic"] -->

---

# Our Solution: Event-Driven Architecture

Redesigned the pipeline using partitioned Kinesis streams with Lambda consumers.

<!-- presenterNote: We replaced the monolithic Kafka consumer with a partitioned Kinesis Data Stream. Each partition triggers a Lambda function that processes events in parallel. This decoupled ingestion from processing. -->
<!-- keyPoints: ["Partitioned Kinesis streams", "Lambda consumers for parallel processing", "Decoupled ingestion from processing"] -->

---

# Implementation Approach

1. Migrated producers to write to Kinesis
2. Created Lambda consumers per partition
3. Added DynamoDB for deduplication
4. Deployed canary alongside legacy system

<!-- presenterNote: The migration took 6 weeks with a team of 3 engineers. We ran both systems in parallel for 2 weeks to validate data consistency before cutting over. The canary deployment caught 3 edge cases before full rollout. -->
<!-- keyPoints: ["6-week migration with 3 engineers", "2-week parallel validation period", "Canary deployment caught edge cases"] -->

---

# Evidence: Performance Results

| Metric | Before | After |
|--------|--------|-------|
| Max throughput | 50K/sec | 500K/sec |
| Data loss rate | 15% at peak | 0% |
| Processing latency | 2.5s | 200ms |
| Monthly cost | $12,000 | $4,500 |

<!-- presenterNote: The 10x throughput improvement came from parallelization across 20 Kinesis shards. Cost reduction was driven by Lambda's pay-per-invocation model replacing always-on EC2 instances. Zero data loss was achieved through Kinesis retry semantics and DynamoDB deduplication. -->
<!-- keyPoints: ["10x throughput improvement", "Zero data loss achieved", "62% cost reduction"] -->

---

# Lessons Learned

- Start with capacity planning before architecture decisions
- Run parallel systems during migration to validate correctness
- Monitor deduplication rates as a health signal

<!-- presenterNote: The biggest lesson was that our original architecture was designed for 10x growth but we needed 100x. Always plan for at least 20x your current peak when designing event pipelines. -->
<!-- keyPoints: ["Plan for 20x current peak", "Parallel systems validate correctness", "Deduplication rates indicate health"] -->

---

# Summary

A well-designed event-driven architecture delivered 10x throughput
at 62% lower cost by decoupling ingestion from processing.
